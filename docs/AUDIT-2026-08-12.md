# NIGHTFALLCOIN — Security Audit of Protocol v4 (Nightproof-α)

**Date:** 2026-08-12
**Scope:** the complete v4 workspace — `nightfall-types`, `-crypto`, `-ledger`, `-consensus`, `-storage`, `-p2p`, `-node`, `-wallet`, `-core`
**Method:** manual review of all 5,097 lines, plus executable proof-of-concept exploits run against the real code
**Verdict:** **v4 was consensus-broken.** Anyone could mint unlimited NIGHT with roughly thirty lines of code, without mining and without owning a single coin. The privacy properties claimed in `ATTRIBUTES.md` were not implemented.

At the time of the audit the live mainnet datadir held 84 blocks, 1,680 NIGHT, exactly one non-coinbase transaction and two distinct recipient keys — i.e. only the operator's own machine. **The vulnerability had not been exploited.**

## 2. Critical findings

### C-01 — The balance proof proves nothing

`crates/nightfall-crypto/src/pedersen.rs`

```rust
pub fn make_balance_proof(inputs, outputs, fee, transcript) -> Option<BalanceProof> {
    let excess_pt = public_excess(inputs, outputs, fee)?;   // computed from public data
    ...
}

pub fn verify_balance_proof(inputs, outputs, fee, proof, transcript) -> bool {
    let expected = public_excess(inputs, outputs, fee)?;    // the SAME computation
    if expected.compress().to_bytes() != proof.excess { return false; }
    ...
}
```

The verifier recomputes the prover's value from the same public inputs and compares it to itself. **This can never fail.** There is no signature, no challenge, no secret — no statement is being proven at all.

Mimblewimble's soundness comes from the excess being *signed under the blinding generator `H`*. Knowing the discrete log of a point with respect to `H` proves that point has no `G` component, which is exactly the statement "this transaction created no value". v4 had no such signature.

**Consequence:** an attacker picks any input amount and any output amount. The transaction validates.

Proof of concept (ran successfully against v4):

```
EXPLOIT 1 CONFIRMED: minted 50000000 NIGHT out of nothing,
total_minted counter still reads 0
```

Fifty million NIGHT — 55 % of the entire supply — in one transaction, with zero mining and zero coins owned.

**Fix (v5):** `crates/nightfall-crypto/src/kernel.rs`. Every kernel carries a Schnorr signature over generator `H` proving knowledge of the excess scalar, and the ledger independently checks the excess equals `Σout − Σin + fee·G − reward·G`. Equality alone is not trusted; the signature carries the soundness.

### C-02 — No range proofs

Pedersen amounts are scalars modulo the group order. Committing to `l − 1` is committing to `−1`. With no range proof, an attacker balances a transaction by creating a negative output, conjuring value while the equation still closes.

```
EXPLOIT 2 CONFIRMED: u64::MAX output note accepted with a 0-value input
```

**Fix (v5):** Bulletproofs (`bulletproofs` 5.0 on Ristretto) on every output, proving `v ∈ [0, 2^64)`. Commitments use `PedersenGens::default()` so they are bit-identical to what the proof system range-proves — using different generators would make the proofs meaningless.

---

### C-03 — Inputs were never checked to exist

`LedgerState::apply_tx` verified that `tx.anchor` equalled the current notes root, but never checked that the notes being spent were actually *in* the tree. There was no Merkle membership proof anywhere in the codebase. `input_commits` was simply whatever the spender wrote.

**Fix (v5):** the ledger keeps an explicit UTXO set. An input references a commitment that must already be present, and the one-time key is read *from the set*, not from the transaction — so a spender cannot substitute a key they control.

---

### C-04 — Signatures did not cover the transaction

`Transaction::auth_transcript()` omitted `input_commits`, `balance_proof`, the output ciphertexts and `auth_pk` itself.

* Inputs could be swapped in flight; the signature stayed valid.
* `auth_pk` was not signed, so anyone could replace the key and signature with their own.
* `txid()` hashed the same incomplete transcript, so `tx_root` committed to almost nothing and transactions were malleable.

```
EXPLOIT 3 CONFIRMED: auth signature and txid do not cover input_commits
```

**Fix (v5):** `body_hash()` covers inputs, outputs, range proofs, encrypted payloads and all kernel fields. Both the kernel signature and every input signature derive from it, and `txid()` is the hash of that body.

---

### C-05 — Corrupting a ciphertext destroyed the recipient's money

Output ciphertexts were unsigned. A relaying node could flip one byte: the transaction still verified, the commitment still entered the tree, and the recipient could never decrypt the note. The funds were permanently unspendable.

```
EXPLOIT 4 CONFIRMED: 5 NIGHT permanently destroyed by a 1-byte flip in transit
```

**Fix (v5):** `Output::commitment_bytes()` includes the payload, and that feeds `body_hash`, which the kernel signature covers.

---

### C-06 — The hard cap was not enforced

`ATTRIBUTES.md` locks `total_minted ≤ 90_000_000 NIGHT` as a binding invariant. The ledger contained no such check. `total_minted_darks` was a plain counter incremented with `saturating_add`, and a forged transaction never touched it at all — the exploit above minted 50 M NIGHT while the counter still read zero.

**Fix (v5):** two independent layers.

1. `SupplyState::would_exceed_cap()` refuses any block whose subsidy would breach the ceiling.
2. A **globally verifiable supply invariant**:

   ```
   Σ UTXO − Σ kernel_excess  =  (minted − burned) · G
   ```

   Anyone can evaluate this in one pass over the chain. If inflation were ever possible, the equation breaks and every node sees it. The node re-checks it after every block and refuses to start on a datadir that violates it. `nightfall-wallet verify-supply` exposes it to users.

### N-01 — A single bad transaction corrupted the node permanently

`apply_tx` inserted nullifiers and updated supply counters **before** verifying the signature, and never rolled back on failure.

```
EXPLOIT 5 CONFIRMED: rejected tx left 1 nullifier(s) in state — any peer can
permanently burn arbitrary nullifiers on your node for free
```

Any peer could send invalid transactions to poison a node's nullifier set with arbitrary values, making legitimate future spends unspendable on that node.

**Fix (v5):** two-stage application. Everything is validated against a staged view first; committed state is touched only once every check has passed. Regression tests assert byte-identical state after a rejected block.

---

### N-02 — The chain could be rewritten for pocket change

Two compounding defects:

1. **Difficulty was "number of leading zero bits"** in a `u32`, clamped to `[8, 28]`, adjusted by ±1 every 240 blocks. The ceiling of 28 bits is ≈ 2.7 × 10⁸ hashes — a few seconds of one CPU core. That was the maximum security the network could ever express.
2. **Fork choice compared `blocks.len()`.** `chain_work()` existed but was never called. A chain with less work but more blocks won.

Combined: publish timestamps twice the target, the retarget drops difficulty toward the floor of 8 bits (256 hashes per block), then mine thousands of near-free blocks and take over by length.

**Fix (v5):**

* Difficulty is a `u64`; a hash is valid when `H · D < 2^256`, computed exactly with 64-bit limbs and no big-integer dependency.
* Retarget every block via LWMA-1 over a 90-block window, clamped to ±2× per block, with a network floor.
* Fork choice compares exact cumulative work (`u128`).
* Median-time-past over 11 blocks; future drift cut from 2 h to 120 s; solve times clamped to `[−5T, +6T]` against time-warp.
* Reorg depth bounded at 500 blocks.

### P-01 — The privacy claim was false

`ATTRIBUTES.md`: *"Sender / receiver / amount — hidden by default"*, *"Anonymity-set goal: protocol-scale"*.

`OutputDescription` carried:

```rust
pub recipient_spend_pk: [u8; 32],   // in the clear, on chain, for every output
```

Every payment named its recipient in plaintext. Repeat payments to the same address shared the field. The entire payment graph was public and the anonymity set was exactly **1**.

```
EXPLOIT 6 CONFIRMED: anonymity set = 1. Recipient graph is fully public.
```

**Fix (v5):** one-sided stealth outputs (`crates/nightfall-crypto/src/stealth.rs`), the construction used by Litecoin MWEB:

```
t   = H(r·A)          shared secret     (receiver recomputes as H(a·Ke))
b   = H("blind" ‖ t)  blinding factor
o   = H("ko"    ‖ t)  one-time key offset
Ko  = B + o·G         one-time output key, published
```

Every output gets a fresh unlinkable `Ko`. Two payments to the identical address share no on-chain field. The recipient scans with their scan key alone; spending requires `b_spend + o`, so **the sender cannot spend what they sent** — the hole that naive non-interactive Mimblewimble has.

---

### P-03 — View keys were claimed but did not exist

`ATTRIBUTES.md` locks *"View keys: Yes (user-controlled)"* and *"ZK disclosure packs"*. Neither existed. Worse, the nullifier was derived from `hash(spend_signing_key_bytes)`, so any credential capable of detecting your outputs would also have been capable of spending them.

**Fix (v5):** the key hierarchy splits into a **scan key** `a` and a **spend key** `b`. A view key is `(a, B)`: it finds every output, reads every amount and memo, and cannot sign. This is enforced by the type system — `ViewKey` has no method returning a spend secret.

## 3. Remaining findings, briefly

| Finding | Detail | v5 |
|---|---|---|
| **N-03** | `mine_block()` ran inside the global mutex. During proof of work the node answered no RPC, accepted no peer block and relayed nothing. | Mining moved out of the lock; the loop aborts within ~4096 hashes when the tip moves. Verified: RPC answered instantly while 445 blocks were being mined. |
| **N-04** | `MerkleTree::root()` cloned every leaf and rebuilt the tree — called once *per transaction*, giving O(n²) per block. | UTXO root is a Merkle tree over the sorted set, O(n log n) per block. A Merkle Mountain Range would make it incremental — that is the next optimisation, not a correctness issue. |
| **N-05** | Whole chain serialized as pretty JSON every 10 s and after every block; whole chain re-downloaded from every peer every 20 s. | Append-only JSONL, only new blocks written. Sync fetches forward from the local tip in bounded batches. |
| **N-06** | `read_line` with no size limit. | 4 MB message cap, enforced before allocation. |
| **N-07** | Any rejected block made the node download the peer's entire chain — free bandwidth amplification. | Removed; divergence is resolved by the periodic sync task. |
| **N-08** | `drain_for_block` took `HashMap::values()` in arbitrary order with no conflict check. Two conflicting transactions both got selected, block assembly failed, mining stalled. | Fee-ordered selection with conflict detection and a 10,000-entry mempool cap. |

| **W-01** | `core.seed` written with the process umask — typically `0644`. Any other account on the machine could read it and steal every coin. | `write_secret_file()` sets `0600`; existing wallets are repaired on open. |

| **W-03** | Addresses were raw hex with no checksum. One mistyped character sent funds into an unspendable void. | `nf1…` encoding with a 4-byte checksum; malformed group elements rejected. |
| **W-04** | The wallet believed whatever amount the sender's ciphertext claimed. | `scan_output` verifies the commitment actually opens to the stated value, and rejects the output otherwise. |

## 4. Economics: the supply is not exactly 90,000,000

The idealised geometric sum is exact:

```
2 × 20 NIGHT × 2,250,000 blocks = 90,000,000 NIGHT
```

But each halving truncates via integer shift (`reward >> halvings`), so the curve actually terminates at

```
89,999,999.70750000 NIGHT   (8,999,999,970,750,000 darks)
```

a shortfall of **0.29250000 NIGHT**.

This is safe — the invariant is `total_minted ≤ cap`, and it holds. But `README.md`, `MANIFESTO.md` and `ATTRIBUTES.md` state the supply *equals* 90 M, which is not true. The number is now pinned by a test (`emission_sums_below_the_cap_and_stops`) so it cannot drift silently. Either the docs should say "just under 90,000,000" or the final era should be adjusted before mainnet.

## 5. What v5 does **not** solve

Stated plainly, because the v4 documentation overstated what it had.

**Mimblewimble does not hide the transaction graph.** Inputs reference specific output commitments. Amounts are confidential and there are no addresses on chain, but an observer can still see *which output was spent by which transaction*. This directly conflicts with `ATTRIBUTES.md`, which locks:

> Anonymity-set goal: **Protocol-scale / full-set class** (not tiny fixed rings)

Mimblewimble does not deliver that on its own. Closing the gap needs kernel aggregation and cut-through at the block level (so individual transactions dissolve into a single block-wide aggregate), and ideally Dandelion++ diffusion at the network layer. **Neither is implemented.** `ATTRIBUTES.md` should either be amended or these must be built before the claim is made publicly.

Also outstanding:

- **No transaction aggregation or cut-through.** Each transaction keeps its own kernel.
- **No network-layer privacy.** No Dandelion++; the node that first relays a transaction is very likely its origin.
- **PoW is still Blake3.** `DECISIONS.md` promised an Argon2id memory-hard variant (Nighthash-v2) "before production economic security". Blake3 is trivially ASIC-friendly and offers no CPU fairness.
- **Startup replays and revalidates the entire chain.** Fine at current heights, linear forever.
- **No headers-first sync**, no UTXO snapshots, no pruning.
- **No third-party audit.** This document is a self-review by the party that wrote the replacement code. Independent review is a prerequisite for any real economic value.

## 6. Verification

Every exploit in this report exists as an executable test.

* `crates/nightfall-ledger/tests/exploit_regression.rs` — the six original attacks, inverted. Each must fail.
* `crates/nightfall-ledger/tests/ledger_flow.rs` — coinbase, transfer, fee burn, double-spend, maturity, atomicity, supply invariant.
* `crates/nightfall-consensus/tests/chain_rules.rs` — work-based fork choice, time-warp resistance, reorg bounds, emission curve.

```
cargo test --workspace
```

99 tests, 0 failures at the time of writing.

End-to-end on devnet: 430 blocks mined, 25 NIGHT sent with an encrypted memo, recipient discovered it by scanning, fee burned, `supply_invariant_ok: true` throughout — and the RPC stayed responsive during active mining.
